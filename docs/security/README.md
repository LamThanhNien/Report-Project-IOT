# AIFOM Security

## Local environment files

Copy `.env.example` to `.env` for local development and replace every placeholder
with a local value. Never commit `.env`, `.env.local`, generated password files,
or any file containing real secrets.

## Default admin account (development only)

The seed command reads `ADMIN_SEED_EMAIL` and `ADMIN_SEED_PASSWORD` from the
environment. Set a strong local password before seeding.

Seed command:

```bash
make seed-admin
# or with custom credentials:
ADMIN_SEED_EMAIL=you@example.com ADMIN_SEED_PASSWORD=<strong-local-password> make seed-admin
```

## JWT configuration

| Env variable        | Default                                      | Notes                        |
|---------------------|----------------------------------------------|------------------------------|
| `JWT_SECRET`        | `changeme-replace-with-a-long-random-secret` | **Must be changed** — backend refuses to start with insecure defaults |
| `JWT_ALGORITHM`     | `HS256`                                      | HMAC-SHA256                  |
| `JWT_EXPIRE_MINUTES`| `1440`                                       | 24 hours                     |

**The backend will NOT start if `JWT_SECRET` is set to a known insecure value or is shorter than 32 characters.** This is enforced by a startup validator.

Generate a secure secret:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Set in `.env`:

```
JWT_SECRET=<output from above>
```

## MQTT authentication (P0 — enabled by default)

Mosquitto now requires username/password authentication. Anonymous connections are **denied**.

### Required local credentials

MQTT credentials must be supplied through `.env`. Docker Compose and the
Mosquitto entrypoint fail startup if they are missing.

### How it works

1. Docker Compose runs a Mosquitto entrypoint script that auto-generates the password file from environment variables.
2. The backend reads `MQTT_USERNAME` / `MQTT_PASSWORD` from `.env`.
3. The ESP32 firmware reads `CONFIG_AIFOM_MQTT_USERNAME` / `CONFIG_AIFOM_MQTT_PASSWORD` from Kconfig/sdkconfig.

### Custom credentials

Set in `.env`:

```
MQTT_ADMIN_USER=<backend-mqtt-user>
MQTT_ADMIN_PASSWORD=<strong-backend-mqtt-password>
MQTT_DEVICE_USER=<device-mqtt-user>
MQTT_DEVICE_PASSWORD=<strong-device-mqtt-password>
MQTT_USERNAME=<backend-mqtt-user>
MQTT_PASSWORD=<strong-backend-mqtt-password>
```

For ESP32, update `iot/firmware/sdkconfig.defaults.local`:

```
CONFIG_AIFOM_MQTT_USERNAME="<device-mqtt-user>"
CONFIG_AIFOM_MQTT_PASSWORD="<strong-device-mqtt-password>"
```

### Regenerating passwords

```bash
bash scripts/generate_mqtt_passwords.sh
```

## Device provisioning (P0)

Device self-registration is now **protected by a provisioning token**.

### How it works

1. Set `DEVICE_PROVISIONING_SECRET` in `.env`.
2. Devices should send `Authorization: Bearer <secret>` or body field `provisioning_token` when calling `POST /api/v1/devices/register`.
3. `?provisioning_token=<secret>` is still accepted for legacy ESP32 demos but is deprecated because query strings are commonly logged.
4. If the secret is empty, device self-registration is **disabled** — admin must pre-register devices.

### For ESP32 firmware

Set in `sdkconfig.defaults.local`:

```
CONFIG_AIFOM_PROVISIONING_TOKEN="aifom_demo_provision_2026"
```

Or in PlatformIO `platformio_local.ini`:

```ini
build_flags =
    -DPROVISIONING_TOKEN=\"aifom_demo_provision_2026\"
```

## Firmware download security (P0)

Firmware binary download now requires authentication.

### Admin download

`GET /api/v1/firmware/{id}/download` requires a valid admin JWT token.

### Device OTA download

`GET /api/v1/firmware/ota-download/{id}?token=<signed_token>` uses a **short-lived signed token**.

- Token is generated by the backend when creating an OTA job.
- Token expires after 30 minutes (configurable via `OTA_TOKEN_EXPIRE_MINUTES`).
- Token is scoped to a specific firmware version, OTA job, and device.
- The token is sent to the device via MQTT as part of the OTA request payload.

## Protected endpoints

| Method | Path | Auth required | Role |
|--------|------|---------------|------|
| `POST` | `/api/v1/auth/login` | None | — |
| `POST` | `/api/v1/auth/register` | None | — (tenant signup only) |
| `GET`  | `/api/v1/auth/me` | ✅ | any |
| `GET`  | `/api/v1/devices` | ✅ | admin |
| `POST` | `/api/v1/devices` | ✅ | admin |
| `POST` | `/api/v1/devices/register` | ✅ provisioning token | — |
| `GET`  | `/api/v1/firmware` | ✅ | admin |
| `POST` | `/api/v1/firmware` | ✅ | admin |
| `GET`  | `/api/v1/firmware/{id}/download` | ✅ | admin |
| `GET`  | `/api/v1/firmware/ota-download/{id}` | ✅ signed OTA token | — |
| `GET`  | `/api/v1/ota/jobs` | ✅ | admin |
| `POST` | `/api/v1/ota/jobs` | ✅ | admin |
| `GET`  | `/api/v1/telemetry` | ✅ | admin |
| `GET`  | `/health`, `/ready` | None | — |

Roles: The platform strictly supports 3 active roles: `admin` (system-wide administration), `tenant_owner` (full CRUD and device/member management within assigned tenant), and `viewer` (read-only tenant data access). Retired roles (`platform_engineer`, `tenant_engineer`) are rejected at authentication and have no access.

## Frontend browser session

Browser sessions use httpOnly cookies for access and refresh tokens. The
frontend sends `credentials: "include"` and uses a non-httpOnly
`aifom_csrf_token` cookie to populate `X-CSRF-Token` on mutating requests.

- On F5 refresh: the client calls `/api/v1/auth/me`, then `/api/v1/auth/refresh`
  if the short-lived access cookie expired.
- On logout: the backend clears auth cookies and the frontend clears local
  session state.
- Legacy Bearer-token API responses can remain enabled for local testers with
  `AUTH_LEGACY_TOKEN_RESPONSE=true`; production must set it to `false`.

## ESP32 Wi-Fi configuration

**Never hardcode Wi-Fi credentials in source code.**

### ESP-IDF firmware (iot/firmware/)

1. Copy `sdkconfig.defaults.local` from `sdkconfig.defaults.local` template.
2. Set your Wi-Fi SSID and password:

```
CONFIG_AIFOM_WIFI_SSID="YourWiFiSSID"
CONFIG_AIFOM_WIFI_PASSWORD="YourWiFiPassword"
```

3. `sdkconfig.defaults.local` is `.gitignored` — never commit it.

### PlatformIO firmware (iot/src/Esp32/)

1. Create `platformio_local.ini` (gitignored):

```ini
[env:esp32doit-devkit-v1]
build_flags =
    -DWIFI_SSID=\"YourWiFiSSID\"
    -DWIFI_PASS=\"YourWiFiPassword\"
    -DMQTT_USER=\"<device-mqtt-user>\"
    -DMQTT_PASS=\"<strong-device-mqtt-password>\"
    -DPROVISIONING_TOKEN=\"aifom_demo_provision_2026\"
```

2. The firmware refuses to start if `WIFI_SSID` is empty.

## Known limitations

1. **Token blacklist required** — readiness fails if JWT revocation storage is unavailable.
2. **Single admin** — no UI to manage multiple users; use `seed_admin.py` or direct DB access.
3. **No HTTPS** — all traffic is plain HTTP in local dev. Use a reverse proxy (nginx/traefik) with TLS in production.
4. **MQTT ACL** — Per-device topic isolation is enforced in production via `infrastructure/mosquitto/config/acl.prod`.
5. **Secrets in `.env`** — `.env` is gitignored, but the file is plain text on disk.

## Manual verification steps

### 1. MQTT anonymous connection should fail

```bash
# Without credentials — should fail
mosquitto_sub -h localhost -t "devices/#" -C 1

# With credentials — should work
mosquitto_sub -h localhost -t "devices/#" -C 1 -u <device-mqtt-user> -P <device-mqtt-password>
```

### 2. Firmware download without auth should fail

```bash
# Without token — should return 401
curl http://localhost:8000/api/v1/firmware/<firmware_id>/download

# With admin token — should return firmware
curl -H "Authorization: Bearer <admin_token>" \
     http://localhost:8000/api/v1/firmware/<firmware_id>/download
```

### 3. Device registration without token should fail

```bash
# Without token - should return 401
curl -X POST http://localhost:8000/api/v1/devices/register \
     -H "Content-Type: application/json" \
     -d '{"device_uid":"test-001","name":"Test"}'

# With token - should succeed
curl -X POST http://localhost:8000/api/v1/devices/register \
     -H "Content-Type: application/json" \
     -H "Authorization: Bearer <DEVICE_PROVISIONING_SECRET>" \
     -d '{"device_uid":"test-001","name":"Test"}'
```
